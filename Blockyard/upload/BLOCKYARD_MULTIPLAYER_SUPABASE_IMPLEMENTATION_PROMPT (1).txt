It already has a Three.js Studio/editor, a custom Lua-like scripting runtime called BloxScript, a Play mode, character rigs and animation support, publishing UI, platform pages, and a separate WebSocket service for collaborative Studio editing.

PART A — REAL MULTIPLAYER FOR PUBLISHED GAMES

A1. Create a separate game-session server
- Add a dedicated service, preferably under `mini-services/game-server/`, with its own package/config and clear run instructions.
- Reuse the existing WebSocket library if appropriate, but do not merge this service into `studio-sync/index.ts`.
- Support multiple game rooms/sessions at once, with unique session IDs, experience IDs, player IDs, room lifecycle, configurable player limits, and clean disconnect handling.
- Provide a simple first matchmaking flow: a player clicks Play on a published public experience; the client joins an available session or creates one; another player choosing the same experience can join the same session until it is full.
- Support private/reserved sessions only if the existing product UI already needs them; otherwise design the interface but do not overbuild them in the first pass.
- Make room capacity configurable. Choose a sensible modest default for the prototype, document it, and do not hard-code an assumption throughout the code.
- Remove the assumption that four bots represent multiplayer. Bots may remain as an optional local testing feature, but online sessions must not spawn four demo bots by default. Do not count bots as real connected players.
- The initial service may keep active session/player state in memory for a single-instance prototype. Document that multiple game-server instances will need a shared coordinator/Redis or equivalent and implement clean interfaces so this can be added. Do not store high-frequency player movement in Postgres.

A2. Authentication and room authorization
- A browser WebSocket cannot generally attach arbitrary custom authorization headers. Authenticate immediately after opening the socket with a first `auth` packet containing the current Supabase access token, then require successful validation before accepting any join or gameplay packet. Apply a short auth timeout and close unauthenticated connections.
- Never trust a client-supplied user ID, username, role, ownership claim, admin flag, player count, or permission. Resolve the verified account identity from the verified Supabase token. Read the display name/avatar from the trusted profile record or validate it against the account.
- Verify JWT signature, issuer, audience, and expiry using a current Supabase-supported validation method. Do not merely base64-decode a JWT or trust its claims without verifying the signature. Do not put access tokens in URL query strings.
- Before joining, verify that the requested experience exists, is published/visible to this user, and that the user is allowed to join it. Prevent guessing a private room ID to bypass game privacy.
- Enforce per-account and per-IP connection/rate limits where practical. Limit packet bytes, packet frequency, malformed packets, chat length, and room count. Validate every packet with a strict schema (Zod or an equivalent already used by the app).
- Give every server message a documented packet type and version. Reject unknown or invalid gameplay packet shapes safely.

A3. First playable multiplayer vertical slice
Implement and verify this minimum end-to-end experience before attempting advanced gameplay:
- Two separate browser tabs/devices can sign in as different users and join the same published game session.
- Both users spawn in the same game map, at valid spawn points.
- Each user sees the other user's avatar/character in the correct approximate position and orientation.
- Walking, jumping, and stopping update remotely with smooth interpolation rather than visible teleporting or jitter wherever possible.
- Join and leave events update the visible player list and remove disconnected characters.
- In-game chat is shared by the people in that session, with server-validated sender identity and message length.
- Reconnection/temporary disconnect has a defined outcome. Avoid duplicate player avatars after reconnect.
- Exiting a game closes the connection and removes remote visual entities/listeners/timers.
- If the server is unavailable, the app should show a clear connection failure and offer Local Play where appropriate. Do not pretend local play is online play.

A4. Server authority — do not build a fake multiplayer relay
- Do not simply broadcast arbitrary x/y/z values sent by clients and call that secure multiplayer.
- For the first MVP, the game server must be authoritative for player identity, session membership, canonical player transforms, movement bounds/speed limits, and important gameplay events. Clients send bounded input intentions (for example directional input, jump request, sequence number, and client timestamp), not unrestricted state changes.
- Reuse/extract the existing PlayController movement and collision logic where feasible. Identify which calculations are browser-only or depend on Three.js/DOM. Extract pure reusable movement/math/collision code where possible so the server can run the same validated rules without importing browser-only renderer code.
- Create a minimal server-side collision representation from the published map's static collidable parts. The first milestone may limit server-authoritative collision to the static geometry/features supported by the current engine, but document the exact limitation. Do not claim arbitrary moving-body physics is server-authoritative if it is not.
- Validate max speed, acceleration, jump, gravity, teleport distance, input cadence, and world bounds. Reject impossible movement and rate abuse. Send authoritative transform snapshots back to clients.
- Implement client-side interpolation between received snapshots. If prediction/reconciliation is added, keep it separate and bounded; do not let client prediction overwrite authoritative state permanently.
- Use a configurable server simulation tick and snapshot rate. Start conservatively (for example, a 20 Hz simulation and a 10–20 Hz network snapshot) and profile before increasing it. Do not broadcast every browser render frame or every React state update.
- Keep transient movement/physics traffic on the dedicated game WebSocket service. Supabase Realtime is not the authoritative physics server and must not be used as a high-frequency position broadcast loop.
- For moving assemblies/vehicles, combat, damage, projectiles, tools, ownership and inventory, do not claim full server authority unless implemented. Establish a clear extension boundary and a roadmap. Do not let a client award itself currency, damage, items, ownership, or admin status.

A5. Remote character rendering
- Reuse the existing character/rig creation and animation systems where practical.
- A remote player should be rendered as a remote-controlled avatar, not another local PlayController instance with keyboard input.
- Remote avatars should receive server-authoritative transform snapshots and interpolate smoothly.
- Ensure remote avatars do not collide as if they were locally controlled unless the design explicitly requires it.
- Avoid creating/destroying meshes on every network packet. Create on join, update transforms, remove on leave.
- Avoid duplicate tick loops and event listeners. Ensure cleanup on unmount, disconnect, game exit, and React Strict Mode remounts.
- Reuse avatar display name/thumbnail safely. Never allow arbitrary untrusted HTML or script injection through names/chat.
- If the local player has an R6/R15 rig or custom avatar, map remote animation states safely. Begin with idle/walk/jump/fall state replication if full animation replication is too large. Do not break the existing Animation Editor or recently fixed animation track behavior.

A6. Shared gameplay events and scripts
- Inspect BloxScript's existing Script, LocalScript, ModuleScript, services, Events, RemoteEvent-like support, and security sandbox.
- Do not run user-authored scripts with unrestricted Node.js access, filesystem access, process access, or arbitrary network access on the game server.
- Design a server/client execution boundary. Server-side actions such as damage, rewards, inventory changes, purchases, and game-state mutations must be validated on the trusted server.
- If implementing server-side BloxScript in this milestone is too large, explicitly implement/document the first safe multiplayer API boundary (for example, validated RemoteEvent/request-response packets) and do not pretend all BloxScript scripts execute server-side.
- Add instruction/time budgets and size/rate limits to any server-executed user code. Keep the existing client sandbox and instruction budget intact.

A7. Studio Team Create remains separate
- Keep `mini-services/studio-sync/` and `src/lib/studio/net.ts` for collaborative editing.
- Add Supabase account authentication and server-side room access checks to Studio sync. A random room name must not grant write access to a project.
- A user must have owner/collaborator permission to edit a project room. Read-only visitors must not be allowed to send part modifications.
- Validate all part payloads and operations. Do not permit arbitrary `parts:sync` to overwrite the whole room unless the sender is authorized and the operation has a safe conflict/version check.
- Preserve existing Team Create behavior and UI as much as possible.

PART B — SUPABASE BACKEND MIGRATION

B1. Use Supabase for the right jobs
Use Supabase as the platform's trusted persistent backend:
- Auth: signup, login, logout, password reset, email verification/session.
- Postgres: user profile records, published experience metadata, experience versions/metadata, collaborators/permissions, asset metadata, favorites/likes/visits if present, moderation records, and eventually purchases/currency ledger.
- Storage: uploaded assets, thumbnails, icons, project snapshots or other large binary/project files, with appropriate access policies.
- Realtime: optional presence for online status/low-frequency room presence, and low-rate chat/notifications where appropriate.

Do NOT use Supabase Realtime Presence to send every player movement update; its own documentation says it is intended for slow-changing state, not high-frequency updates. Use the dedicated game-server WebSocket for live gameplay. Do not put the authoritative game physics loop inside a Supabase Edge Function or Postgres trigger.

B2. Supabase client setup for this project
- Confirm this is Next.js 16.x and follow the CURRENT official Supabase Next.js SSR instructions.
- Install the documented packages only if missing: `@supabase/supabase-js` and `@supabase/ssr`.
- Create separate browser and server client helpers using the currently supported `createBrowserClient` and `createServerClient` patterns.
- For Next.js 16 use the current `proxy.ts` session-refresh pattern as documented for Next.js 16. Do not blindly create a `middleware.ts` file from an old tutorial. Ensure cookie handling is correct for the installed Next.js version.
- Use cookie-based SSR auth with the PKCE flow as recommended by current Supabase docs. Use a server-side user/claims verification method in protected Route Handlers and Server Actions.
- Do not store the authoritative session in a custom localStorage password/session scheme. The Supabase client may manage its documented browser session mechanism, but server checks must use verified Supabase auth and cookies/tokens.
- Use environment variables with names that are explicit and documented. Recommended baseline:
  `NEXT_PUBLIC_SUPABASE_URL=`
  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=`
  `SUPABASE_SECRET_KEY=` (optional server-only key only if genuinely needed for trusted admin tasks; never prefix with NEXT_PUBLIC)
  `GAME_SERVER_URL=`
  `GAME_SERVER_INTERNAL_SECRET=` (only if the architecture genuinely needs service-to-service authentication; server only)
- Never expose `SUPABASE_SECRET_KEY`, internal secrets, Postgres passwords, signing keys, or other privileged credentials in client bundles, browser storage, public API responses, logs, or committed files.
- Prefer user-scoped queries and RLS. If a privileged server operation needs the secret key, isolate it in a server-only module and use it only for the specific trusted operation. Never use the secret key as a shortcut around designing RLS.

B3. Migrate the current browser-local platform data safely
Inspect `src/lib/studio/auth.ts`, `src/lib/studio/platform.ts`, `src/lib/studio/webdata.ts`, and every call site before changing behavior.
- Replace browser-local accounts/passwords/session/roles with Supabase Auth and a `profiles` table.
- Never upload existing raw passwords from localStorage. Existing local demo users must sign up again or use a clearly explained account migration/reset path. Do not claim their old passwords were migrated.
- Provide a safe optional local-data export/import path for the user's own non-secret projects and assets. Never migrate local admin flags, bans, privileges, or user-supplied balances as trusted values.
- Migrate published game metadata to Postgres and project/asset blobs to Supabase Storage or an appropriate structured version table. Determine from the current serializer what needs to be persisted. Do not put enormous binary payloads directly in ordinary metadata rows.
- Preserve local unsaved Studio drafts and offline work. Clearly separate local draft/cache storage from cloud-published canonical data.
- After successful cloud save/publish, show clear saved/published status and errors. Avoid deleting the local draft until the cloud write has been confirmed.
- On users without Supabase environment configuration, show a clear configuration message or safe prototype-only mode. Do not crash the entire Studio.

B4. Database schema and migration files
Create reproducible SQL migrations under `supabase/migrations/` (initialize `supabase/` if necessary). Derive exact columns and JSON shapes from the current Blockyard types and serializers; do not guess or silently discard fields.

At minimum, assess and implement tables equivalent to:
- `profiles`: `id` references `auth.users`, unique username/handle, display name, avatar reference, timestamps. Profile roles/privileges must not be client-editable.
- `experiences`: owner, title, description, visibility/publication state, thumbnail/storage references, active version, created/updated timestamps.
- `experience_versions`: experience ID, version number, serialized project snapshot/storage path, creator, published flag and timestamp. Preserve revision history rather than overwriting every version.
- `experience_collaborators`: experience ID, user ID, explicit role/permissions, created timestamp, unique membership constraints.
- `assets`: owner, storage path, type, metadata, visibility and timestamps.
- `favorites`/`likes`/`visits` only if those features exist in the project and are actually used. Use uniqueness constraints to prevent duplicate likes/favorites.
- `moderation_reports` and `moderation_actions` only if matching existing UI/workflows are present; moderation authority is server-only.
- `purchases` and `currency_ledger` only as a carefully designed future/next-stage migration if the prototype's current marketplace needs them. All balance changes must be atomic server-side database transactions/RPCs with audit records, idempotency keys and constraints. Never trust a client-provided balance or price.
- active game sessions may have a small session registry/heartbeat table if needed for discovery, but do not store every player transform in Postgres.

Define foreign keys, indexes, unique constraints, timestamps, delete behavior, and JSON schema validation/versioning where appropriate. Add migration rollback notes where safe; avoid destructive rollback assumptions for real user data.

B5. RLS and database security — mandatory
- Enable Row Level Security on EVERY table exposed through the Supabase Data API.
- Explicitly set grants and policies for each operation, rather than relying on vague broad access. A policy does not remove an existing table grant.
- Public visitors may read only published/public experience data and public profile fields that are intentionally public.
- An owner can create/update/delete their own experience metadata and versions. Collaborators can only perform actions allowed by their explicit collaborator role.
- Users can read/update only their own private profile fields. Do not allow clients to modify admin roles, moderation decisions, currency, purchase results, ownership, or trusted counters.
- A user cannot claim another user's ID on insert/update. Use `auth.uid()` and verify row ownership in policies.
- Keep private project snapshots and private assets inaccessible to unrelated users. Public thumbnails may be public only if intended.
- Add Storage bucket policies that restrict user uploads to a folder keyed by the authenticated user's ID, and allow reading only when the experience/asset visibility policy permits it.
- Avoid recursive RLS policy patterns. Add indexes for fields used in policies.
- Treat the service/secret API key as an RLS-bypass credential. It must remain server-side and must never be used in client code.
- Add SQL policy tests under `supabase/tests/` for allowed AND denied access. If Supabase CLI/pgTAP is available, run `supabase test db`; otherwise provide reproducible tests and report that they were not run.

B6. Authentication UI and API conversion
- Update login/signup/logout/password-reset flows to call Supabase Auth rather than comparing localStorage passwords.
- Add server-side session validation to protected API routes and publishing actions.
- Update the profile creation flow safely. Use a database trigger or trusted server flow for creating the initial profile row; never allow a client to assign privileged roles.
- Add clear loading/error/signed-out states. Prevent duplicate submissions.
- Do not expose email addresses or private profile fields in public profile APIs.
- Remove any visible hard-coded demo admin password or client-seeded admin credential. Build a secure server-side admin bootstrap process, documented as manual and restricted.
- Update the Admin UI so every admin action is authorized on the server, not merely hidden in React.

B7. Asset/project storage
- Create named buckets based on actual project needs (for example, private `experience-files` and a public `experience-thumbnails` bucket only if thumbnails are meant to be public).
- Store metadata in Postgres and binary/project snapshots in Storage where appropriate.
- Use owner-scoped object paths, upload size limits, allowed MIME types, and Storage RLS policies.
- Validate uploads server-side. Do not trust a browser-provided content type or filename.
- Do not expose private storage paths or signed URLs permanently. Use appropriate signed URLs for private assets.
- Add upload progress/error handling and preserve local drafts if an upload fails.

## F3. Special requirement: aggressively test login bypass and `player 0` / `player 1` / numeric-ID mistakes

The owner specifically wants login bypass and the kind of bug where a player/account numbered `0` or `1` is accidentally treated as logged in, privileged, or another user to be checked. Treat this as a mandatory authorization test category.

Search the whole codebase for `userId`, `playerId`, `ownerId`, `accountId`, `id`, `uid`, `role`, `admin`, `isAdmin`, `isOwner`, `authenticated`, `loggedIn`, `session`, `token`, `permissions`, `localStorage`, `sessionStorage`, URL/query parameters, and WebSocket packet fields. Inspect truthiness checks such as `if (userId)`, `if (!userId)`, fallback expressions, `Number(userId)`, `parseInt(userId)`, `role === 1`, `admin === 1`, `Boolean(value)`, and assumptions that IDs are nonzero.

Required behavior:
1. An unauthenticated request stays unauthenticated even if it sends `userId=1`, `playerId=1`, `userId=0`, `admin=true`, `role=admin`, `isLoggedIn=true`, or a forged localStorage entry.
2. A user cannot become another user by changing a URL, JSON body, WebSocket packet, cookie, local-storage field, or numeric ID.
3. A normal user cannot become an admin by changing `role`, `permission`, `admin`, or `isAdmin` to `1`, `true`, or a string.
4. A player ID is not proof of identity. The server binds the connection to the authenticated Supabase subject after verifying the access token.
5. Object ownership is checked against the server-derived identity and actual database permissions on every read/write operation.
6. Missing, null, empty, malformed, negative, out-of-range and unexpected-type identifiers fail safely.
7. Do not rely on truthiness for identifiers. Use strict schema validation and explicit authorization comparisons.
8. If numeric IDs remain for legacy data, never use their value as a privilege level or identity assertion.

Add regression tests with User A, User B, an unauthenticated client, a normal user, and an administrator fixture. Test cross-account access to private projects, profiles, assets, session membership, inventory, currency, roles and published experience ownership. Verify rejection at the server/database layer, not merely by hiding UI controls.

## F5. CSRF, OAuth, third-party login and browser-boundary security

Determine the real authentication transport for each endpoint. Do not apply generic CSRF instructions without checking whether requests use cookies, bearer headers or both.

Protect account updates, publishing, project deletion, purchases, collaborator changes and admin actions. CORS is not a CSRF defense. For OAuth and third-party identity providers:
- Use supported Supabase Auth flows and PKCE where applicable.

- Do not log authorization codes, access tokens, refresh tokens or password-reset tokens.

## F6. Memory overflow, resource exhaustion and denial-of-service hardening

The owner specifically wants memory overflow risks examined. In JavaScript/TypeScript, the most relevant practical web-server risks are often unbounded allocation, memory exhaustion, stack exhaustion, CPU exhaustion, leaks, oversized decoded assets, and resource-usage bugs. Do not incorrectly claim that ordinary JavaScript has the same raw pointer-based buffer-overflow behavior as C. However, inspect native addons, WebAssembly and native media/model libraries separately because their memory safety model can differ.

Inspect all allocations and resource lifetimes, especially:
- `JSON.parse`, request body parsing and response serialization.
- Array and typed-array creation from user-supplied lengths.
- Buffer allocation and file reads.
- Image and texture decoding.
- GLTF/model/archive import and decompression.
- Project snapshot loading and cloning.
- Recursive traversals, graph walks and physics broad-phase calculations.
- Game-room/player/chat history collections.
- WebSocket send queues and pending promises.
- BloxScript tables, arrays, nested values, recursion and execution loops.
- Three.js geometry, materials, textures, render targets and event listeners.
- Timers, observers, workers and subscriptions after player/room/session teardown.

Add configurable hard limits and reject oversized input before allocating or parsing it. Derive and document limits from actual game formats and measured resource use. At minimum, bound:
- HTTP request body size.
- WebSocket message size (start with a conservative 64 KiB limit for ordinary control packets; use a separate authenticated streaming/upload path for larger assets).
- Connections per account/IP and sessions per owner.
- Players per game session; rooms and pending joins; reconnect attempts.
- Chat length and message rate.
- Parts, scripts, nested properties, keyframes and assets per project.
- Compressed and decompressed project snapshot sizes.
- Image width, height, pixel count and decode time.
- Archive file count, nesting, per-file size, total uncompressed size and compression ratio.
- JSON depth, array length and total object/property count.
- Script instruction count, wall-clock budget, recursion depth, table allocation budget and event emission rate.
- Physics entity count, collision pair count, simulation time budget and pathfinding complexity.
- Queue depth, cache size, retained history and log buffer size.

Additional defenses:
- Stream large legitimate uploads instead of buffering arbitrary files fully in memory.
- Use bounded queues and backpressure for WebSocket sends.
- Close idle/dead sockets and clean up resources after disconnect.
- Put untrusted or expensive script execution in a constrained worker/process where feasible; never block the main server event loop.
- Add event-loop lag, heap/external memory, room count, connection count, queue depth and script-budget metrics.
- Add timeouts/cancellation for costly work.
- Cap recursion depth and avoid catastrophic-backtracking regex on user input.
- Check numbers with `Number.isFinite`, safe-integer/range validation and dimension/size caps before arithmetic or allocation.
- Dispose Three.js geometries, materials, textures and render targets; detach listeners when players, games, previews or sessions are destroyed.
- Test repeated create/join/leave/load/unload cycles for heap growth and listener leaks.
- Do not run catastrophic memory/CPU tests against production. Use isolated local/staging tests with small controlled budgets. Success means clean rejection, timeout or cleanup—not crashing the host.

Create safe tests for oversized request bodies, deeply nested JSON, enormous arrays, extreme image dimensions, decompression-bomb-like archive metadata, malformed models, repeated join/leave cycles, slow WebSocket consumers and script-budget exhaustion. Ensure rejection happens before expensive allocation wherever possible.

## F7. Supabase/Postgres-specific hardening

Treat Supabase security as a database authorization problem, not merely client SDK setup.

For every table in an exposed schema:
- Enable RLS.
- Set explicit table grants; RLS policies and SQL grants are separate controls.
- Create explicit policies for SELECT, INSERT, UPDATE and DELETE as appropriate.
- Test allowed and denied access for `anon` and `authenticated` roles.
- Use `auth.uid()` or a server-derived verified identity for ownership checks.
- Do not use user-editable `raw_user_meta_data` as an authorization source.

- Inspect views, functions, RPCs, triggers, Storage policies and exposed schemas for RLS bypass paths.
- Review `SECURITY DEFINER` functions, search_path, ownership and grants carefully.

- Keep service/secret keys exclusively server-side; never expose them through `NEXT_PUBLIC_*`, browser bundles, source maps, logs or error messages.
- Never use a privileged service key in browser code.
- Ensure user-supplied `user_id`, `owner_id`, `role`, `balance`, `is_admin`, `verified`, `published`, and `permissions` cannot override server-derived values.

- Test signed URL expiry and authorization.

## F8. WebSocket and multiplayer-specific security

Audit BOTH the existing Studio sync server and the new published-game server.

- Authenticate a socket before accepting room membership or sensitive messages.
- Validate the exact `Origin` against an allowlist to prevent cross-site WebSocket hijacking.
- Bind the authenticated Supabase subject to the server-side socket context; never trust `playerId`, `userId`, `ownerId`, `admin`, or role fields in packets.
- Authorize every packet against the current user, game, room and action. A successful handshake does not authorize every later operation.
- Use strict versioned schemas for every packet type and reject unknown fields/types where appropriate.
- Use payload limits, rate limits, per-room/per-user quotas, heartbeats, idle timeouts and backpressure.
- Never broadcast private profile fields, email addresses, access tokens, internal moderation state or server secrets.
- Prevent clients from choosing another player's identity or overwriting another player's transform.
- Validate sequence numbers, timestamps and movement-update rates; stale/replayed messages must not roll state backward.
- Validate server-side actions such as damage, inventory changes, purchases, tool use and physics events.
- A guessed room ID must not grant access. Enforce private/invite-only room permissions.
- Avoid logging full socket auth payloads or tokens.
- On disconnect, remove presence, subscriptions, timers, player entities, buffers, listeners and queued messages.
- Slow clients must not grow unbounded send queues or stall the server.

Create negative tests for forged user IDs/player IDs, joining another user's private room, unauthorized Studio edits, fake admin packets, oversized messages, message floods, invalid schemas, stale/replayed state updates and cross-origin socket handshakes.

## F9. Secure BloxScript and creator-created content

BloxScript is an attack surface because Blockyard users can author scripts. A scripting language is not safe merely because it is not JavaScript.

- Never evaluate BloxScript by passing it into host `eval`, `new Function`, Node `vm` without suitable isolation, or arbitrary dynamic import.
- Keep a strict allowlist of available APIs, objects, services and capabilities.
- User scripts must not access `process`, filesystem, environment variables, arbitrary network sockets, database credentials, internal server APIs or host globals.
- Separate client scripts and server scripts. Server-only capabilities must never be exposed to client scripts.
- Every server API invoked from a client script independently authenticates, authorizes and validates parameters.
- Add instruction, time, recursion, memory/table, event and output budgets.
- Infinite loops, recursive explosions, huge table creation, massive event firing and deeply nested values must terminate safely.
- One player's script must not read another player's private data or server secrets.
- Validate RemoteEvent/RemoteFunction-like calls on the server.
- Clients must not decide their own currency, health, inventory, admin status, game ownership, damage, purchase result or trusted physics state.
- Test sandbox boundaries with harmless capability probes and expected-denial tests in local/staging only.
- Document the supported BloxScript API and mark unsupported Roblox APIs honestly.

4. RLS and database tests.
5. Local API and WebSocket authorization tests.
6. Browser tests with two authenticated users and one unauthenticated session.
7. Controlled resource-limit and fuzz tests in an isolated local/staging environment.
8. Build/deployment configuration review.

## F12. Security headers, transport and deployment boundaries

Inspect hosting and deployment configuration for the website, Supabase, Studio sync service and game server.

- Enforce HTTPS/WSS in production.
- Redirect insecure HTTP to HTTPS at the hosting edge where appropriate.
- Set secure cookies with HttpOnly, Secure and suitable SameSite attributes where the auth model requires cookies.
- Configure CSP and other security headers based on actual app behavior. Avoid policies so broad they provide no meaningful protection.
- Set exact CORS and WebSocket origin allowlists.
- Avoid public admin/debug endpoints.
- Disable verbose stack traces and debug routes in production.
- Apply least-privilege process/container permissions.
- Keep production secrets in host secret management, not the repository.
- Restrict outbound network access where feasible for services that fetch external URLs.
- Separate the public web app from the internal game-server management interface.
- Protect health/metrics endpoints; expose only non-sensitive health status publicly.
- Document reverse-proxy/WebSocket timeout and body-size settings.
- Ensure rate limits are enforced server-side and cannot be bypassed by changing a client setting.

## F13. Mandatory security deliverables

In addition to the multiplayer/Supabase deliverables, create:

1. `SECURITY_AUDIT.md` — dated audit report with scope, architecture, sources reviewed, tools run, confirmed vulnerabilities, suspected risks, false positives and untested areas.
2. `SECURITY_THREAT_MODEL.md` — assets, trust boundaries, attacker types, abuse cases, threats, mitigations and residual risks for Studio, published games, Supabase, Storage, OAuth, WebSockets and BloxScript.
3. `SECURITY_TEST_PLAN.md` — test cases for authentication, login bypass, authorization, cross-account IDOR, XSS, CSRF, WebSocket abuse, resource exhaustion, file uploads, dependency risks and RLS.
4. `SECURITY_FIXES.md` — every actual code fix, affected file, root cause, before/after behavior and regression test.
5. `SECURITY_DEPENDENCIES.md` — dependency scan results, package versions, advisory links, affected-version analysis, update decisions and remaining risk.
6. `SECURITY_OPERATIONS.md` — secret rotation, backups, incident response basics, logging/monitoring, patching cadence and production configuration checklist.
7. Automated security regression tests in the existing test structure.
8. A security checklist in README or the release process.

Prioritize findings as follows:
- Critical: unauthenticated remote compromise, auth bypass, cross-account access to private data, secret leakage, privilege escalation, arbitrary server code execution, or an exploitable critical dependency reachable in production.
- High: cross-account data modification, stored XSS with sensitive session impact, server-side script sandbox escape, high-impact WebSocket authorization bypass, serious resource exhaustion or exposed admin function.
- Medium: limited unauthorized data access, reflected/self-XSS with constraints, missing hardening requiring additional conditions, moderate resource abuse.
- Low/Informational: defense-in-depth gaps, non-sensitive metadata exposure, minor hardening and documentation issues.

For every finding record:
- Finding ID and severity.
- CWE and OWASP mapping where appropriate.
- Affected file/component/endpoint/table.
- Evidence and reproducible local test case (safe and non-destructive).
- Preconditions and likely impact.
- Whether it is confirmed, suspected or not applicable.
- Exact remediation.
- Regression test name and result.
- Residual limitations.

Do not publish secrets, real personal data or operational exploit instructions in the report. A finding must be reproducible by the project owner without attacking an external system.

## F14. Security release gate and acceptance criteria

Do not call Blockyard production-ready merely because the login page works or a scanner shows no findings.

Before recommending a public launch:
- No known unresolved Critical finding.
- No known unresolved High finding without documented risk acceptance and mitigation plan from the owner.
- All privileged endpoints enforce server-side identity and authorization.
- Cross-account tests show private projects, assets, profiles and room state are isolated.
- No client can self-assign admin, ownership, currency, purchase or trusted player identity.
- Supabase RLS and grants have negative tests and pass.
- WebSocket auth, origin validation, packet validation, quotas and cleanup have tests.
- XSS and CSRF tests are run for relevant flows.
- Upload, request, script, world and memory limits exist and are enforced before expensive allocation.
- No unresolved known-exploited dependency vulnerability affects a reachable production component.
- Secret scanning finds no active credentials in source or build artifacts.
- Production build and type checking pass without ignored TypeScript errors.
- Security logs contain useful audit events but never raw passwords, bearer tokens, refresh tokens or secret keys.
- Documentation identifies functionality that is still demo-only or not server-authoritative.

If a full audit is too large for one run, do not pretend it is complete. Finish the highest-risk vertical slice first: login/session verification, authorization and user-ID spoofing, Supabase RLS/grants, WebSocket room membership, XSS sinks, resource limits and dependency/secret scanning. Then list every unreviewed area with explicit status and next steps.

## F15. Required final security summary

In the final response, add a security summary table with these columns:

| Area | Status | Confirmed findings | Fixes made | Tests run | Remaining risk |

Use only these status labels: PASS (tested), PARTIAL (some controls implemented or tests incomplete), FAIL (confirmed unresolved issue), NOT TESTED, or NOT APPLICABLE.

Separately list:
- Public vulnerability sources and advisories actually consulted.
- Installed dependency versions with relevant advisories.
- Confirmed vulnerabilities patched.
- Suspected findings not yet confirmed.
- Exact security tests run and results.

Do not write “fully secure,” “unhackable,” or “all vulnerabilities fixed.” Security is continuous. State audit scope and limitations honestly.

**Security instruction:** Before implementing new multiplayer functionality, inspect and address the highest-risk security weaknesses in the affected authentication, authorization, Supabase and WebSocket paths. Build the feature securely from the beginning. Do not postpone authentication and authorization hardening until after multiplayer is connected.
